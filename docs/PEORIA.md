# 신페리오 — 9단계 v0.3.9

9단계 준비의 저장/조회 구조 위에 실제 계산, 재계산, 앱 결과·이력·당시 점수 화면을 연결했습니다. 앞서 제안한 두 기준에 대해 사용자가 ‘다음’으로 개발 계속을 지시한 범위로 구현했습니다.

## 시간과 권한

- 서버 ended_at부터 3시간 미만. 정확히 3시간이면 신규 계산이 잠깁니다. 자동 종료도 이미 저장된 서버 종료 시각 기준입니다.
- 생성자 또는 종료 권한을 위임받은 참여자만 최초/재계산을 실행합니다. 위임은 기존 종료 권한 설정을 사용하며 종료 전에 관리합니다.
- 기존 참여자와 현재 received 개인 기록 수신자는 전체 결과를 조회합니다. 미참여 수신자는 계산하지 못합니다.
- 최초 1회 + 재계산 2회 = 총 3개 결과이며 순번·과거 결과를 보존합니다. 재계산과 수신은 기한을 연장하지 않습니다.
- 본인 점수 수정은 기존대로 종료+24시간입니다. 계산 마감 후의 점수 수정도 과거 결과를 바꾸지 않으며 신페리오 재계산 기한을 연장하지 않습니다.

## 계산 방식 v1

계산 방식 ID는 `new-peoria-par72-doublepar-hcp0to36-v1`입니다. 대회 방식에는 여러 변형이 있으므로 이번 앱에서 사용하는 방식을 명시하고 이력에 버전을 남깁니다. 개인의 공식 핸디캡 인덱스가 아닙니다.

- 18홀 PAR 합계 72. 9홀과 그 외 PAR 합계는 이 버전에서 계산하지 않고 사유를 안내합니다.
- 전·후반 각각 6홀, PAR 합계 24인 조합을 서버에서 무작위 선정합니다. 총 숨김 12홀·PAR48입니다.
- 해당 전/후반에서 PAR3 1개·PAR4 4개·PAR5 1개의 조합이 가능하면 그 조합 집합을 사용합니다. 그 구성이 없으면 6홀·PAR24인 모든 조합을 사용합니다. 유효한 조합이 없는 코스는 안내 후 차단합니다.
- 후보 조합마다 같은 확률을 적용합니다. 서버 crypto.getRandomValues와 rejection sampling으로 인덱스를 선정합니다. 각 계산에서 새로 추첨하되 우연히 같은 조합이 나올 수 있습니다.
- 같은 실행의 모든 선수에게 같은 숨김 홀을 사용합니다. 사용자가 직접 선정하거나 API로 주입할 수 없습니다. 숨김 홀 목록과 중간 합계를 공개하지 않습니다.
- 18홀 모두 숫자 점수인 선수만 포함합니다. 미완료자는 명단과 입력 홀 수를 보여 주고 제외 확인 후 계산합니다.

각 숨김 홀의 계산용 타수는 `min(실제 타수, PAR × 2)`입니다.

```text
숨김 합계 = 선정된 12홀의 계산용 타수 합계
핸디캡 = max(0, min(36, (숨김 합계 × 1.5 − 72) × 0.8))
총타수 = 실제 18홀 타수 합계 (더블파 제한을 적용하지 않음)
네트 점수 = 총타수 − 핸디캡
```

계산은 정수 0.1타 단위로 처리합니다. `핸디캡×10 = clamp(숨김합계×12−576, 0, 360)`이므로 중간 부동소수점 반올림에 따라 동점이 갈리지 않습니다. 낮은 네트 점수부터 정렬하고 동점은 1,1,3 공동 순위입니다. 동점 행의 표시 순서는 당시 선수 순서를 유지합니다.

예: 모든 홀 PAR4, 모든 홀 5타이면 총90타, 숨김합계60, 핸디캡14.4, 네트75.6입니다. 과도한 홀 점수는 핸디캡 계산에만 제한되며 원본 점수나 총타수를 바꾸지 않습니다.

기본 구조·수식·일반적인 더블파/36 제한은 [사이타마 국제 골프클럽의 공식 안내](https://www.saikoku.com/newrule.html)를 대조했습니다. 하한0, PAR72 지원 범위, 동점 순위, 비표준 구성 시 PAR24 후보 선정은 이 앱의 명시적 구현 기준입니다. 클럽 안내는 핸디캡 상한 없는 변형도 설명하므로 위 기준을 모든 대회의 유일한 표준으로 설명하지 않습니다.

## 저장과 공개 조회

기존 `0007_peoria_history.sql`을 사용하며 이번 버전은 새 마이그레이션이 없습니다. peoria_runs의 새 행에 시각/계산자/당시 이름, 원본 버전/계산 방식 버전, 당시 코스명/PAR/전체 선수/원본 점수, 대상/제외 슬롯, 결과/순위, 내부 숨김 홀, 실행 요청 ID/해시를 함께 저장합니다.

순번은 정수 1~3, (round_id,ordinal)은 유일합니다. 성공한 실행은 새 INSERT만 하며 결과 UPDATE/DELETE API는 없습니다. DB 관리자의 직접 SQL 수정을 막는 구조는 아닙니다.

읽기는 숨김 홀/내부 요청 정보를 SELECT에서 제외하고 저장 JSON도 공개 필드만 새 객체로 만듭니다. 누락되거나 잘못된 이력은 내부 내용을 응답에 넣지 않고 오류를 반환합니다. 당시 이름과 점수를 현재 원본으로 바꾸지 않습니다. 개인 기록 삭제로 비참여 수신자가 조회 권한을 잃어도 공동 이력은 유지합니다.

## 확인과 원자적 실행

1. GET에서 시간·권한·완주/미완료 명단·현재 이력 수를 확인합니다. 코스/선수/점수 Snapshot, 원본/권한 버전, 종료 시각, 계산자 이름, 기존 이력 ID로 confirmation_token을 만듭니다.
2. 앱은 최신 GET 뒤 명단과 미완료 제외 여부를 보여 줍니다. 재계산이면 새 추첨으로 순위가 바뀔 수 있고 횟수 1회를 사용하며 이전 결과는 보존된다고 안내합니다.
3. POST는 확인한 버전·이력 수·토큰과 명시적 확인 플래그를 보냅니다. 서버가 새로 읽은 상태와 다르면 peoria_changed로 새 확인을 요구합니다. 사용자 지정 숨김 홀 등 알 수 없는 필드는 거절합니다.
4. 서버 계산 뒤 D1 batch 안에서 활성 기기, 종료 상태, 권한, SQL 서버 시각, 원본/권한 버전, 이력 수, 계산자/선수 이름과 연결을 재검사합니다. 모든 저장 정보는 하나의 새 행으로 원자적으로 삽입합니다.
5. 계산은 원본 점수, rounds.record_version/updated_at/ended_at, 종료 완료 Snapshot, 통계, 광고 이력을 변경하지 않습니다.
6. 동시 같은 요청은 같은 run_id를 받습니다. 다른 요청이 먼저 실행됐다면 명단·횟수를 다시 확인해야 하며 네 번째 결과는 만들 수 없습니다.
7. 같은 요청 ID/본문은 이미 성공했다면 기한/횟수 마감 후에도 기존 run_id를 재확인합니다. ID만 재사용하고 본문을 바꾸면 request_reused입니다. 활성 기기 인증은 재확인에도 필요합니다.

D1의 원자적 batch와 실패 롤백은 [Cloudflare 공식 문서](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)를 기준으로 기존 mutation_guards 패턴을 사용합니다. 거절된 추첨은 이력/횟수에 남지 않고 클라이언트로 보내지 않습니다.

## 기기 보관과 앱 화면

사용자별로 확정한 원래 요청을 AsyncStorage에 먼저 저장합니다. 로컬 쓰기에 실패하면 서버 호출하지 않습니다. 한 사용자에게 확인 중인 실행 요청은 하나이며 새 요청으로 교체하지 않습니다. 같은 기기의 동시 동작을 직렬화하고 Web에서는 Web Locks도 사용합니다.

- 통신 실패/응답 유실/429/서버 오류는 같은 요청을 유지합니다. 앱 재실행 시 홈의 ‘신페리오 결과 확인 이어서’로 복귀해 명시적으로 재확인합니다. 자동으로 새 계산을 하지 않습니다.
- 서버 성공 뒤 로컬 요청 정리 실패도 원래 요청을 유지하여 중복 없이 재확인합니다.
- 확정된 4xx 거절은 실행되지 않은 요청으로 표시합니다. ‘최신 상태 확인’으로 해당 요청을 정리한 뒤 새 명단을 확인할 수 있습니다. 결과를 모르는 요청에는 폐기 버튼이 없습니다.
- 사용자 변경/기기 이전 시 요청을 다른 user_id로 전송하지 않습니다. 저장소가 손상되면 원본을 임의로 지우지 않습니다.

종료 화면·종료 요약과 받은 기록 상세에서 진입합니다. 최신 결과가 기본이며 이전 결과 선택, 당시 전체 스코어카드 보기, 계산 기준 보기를 제공합니다. 원본 버전이 바뀌면 과거 점수 기준임을 안내합니다. 한국어/영어 리소스를 분리했습니다.

신페리오 계산 자체에는 전면 광고가 없습니다. route의 origin=round/record를 유지하며 후속 배너 연결 시 종료 흐름은 제외, 개인 기록 일반 열람은 대상입니다. 실제 광고 SDK/배너는 아직 연결하지 않았습니다.
