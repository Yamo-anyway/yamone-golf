# 7단계 기록 전달 — v0.3.6

## 서로 다른 데이터

ROUND는 공동 원본 하나입니다. DELIVERY는 특정 Player Slot에 연결된 사용자에게 보낸 한 번의 전송입니다. RECEIPT는 그 사용자가 전체 라운드를 자신의 개인 목록에 받은 사실입니다. 점수를 여러 개인 복사본으로 나누지 않으며 수신한 라운드의 전체 코스/플레이어/홀별 점수/순위를 조회합니다.

9단계 준비(v0.3.8)에서 응답의 peoria_runs를 원본 라운드의 저장 이력에 같은 수신 권한으로 연결했습니다. 계산 쓰기는 정책 확정 후 연결하므로 아직 실제 생성된 이력이 없으면 빈 배열입니다. 8단계의 통계는 수신자와 연결된 본인 Player Slot만 사용해야 합니다.

## 보내기와 연결

- 기존 라운드 참여자는 종료된 라운드의 연결된 Player Slot에 기록을 보냅니다. 사용자 코드/QR 확인과 슬롯 버전 검사를 사용합니다.
- 연결된 사용자여도 실제 라운드에 참여하지 않았다면 플레이어 관리·보내기 권한은 없습니다. 받아간 전체 라운드를 읽을 수 있습니다.
- 전송 대기는 round/slot/recipient당 하나입니다. 같은 요청 재시도나 이미 대기 중인 전송을 다시 누르면 기존 항목으로 연결하고 요청 별칭도 기록합니다.
- 이미 활성 개인 기록이 있으면 추가 전송하지 않습니다. 삭제 후 명시적으로 다시 보내면 새로운 delivery_id를 생성합니다.
- 전송은 pending → received 또는 pending → cancelled입니다. 수신 완료를 다시 pending으로 되돌리지 않습니다.
- 보낸 사람, 라운드 생성자, 받는 사람은 pending 전송을 취소할 수 있습니다. 받는 사람의 버튼은 ‘받지 않기’입니다. 이미 받은 전송은 취소로 되돌릴 수 없습니다.
- 종료 후 사용자 연결/해제와 미등록 이름 변경은 기존 참여자에게 허용합니다. 슬롯/점수/수신 이력을 지우지 않으며 활동·종료 시각을 바꾸지 않습니다.
- 연결 해제와 pending 전송 취소는 같은 트랜잭션입니다. 수신이 먼저 끝났다면 기존 개인 기록은 원래 수신자에게 남습니다. 연결 해제로 기존 수신 기록의 소유자를 바꾸지 않습니다. API current_player는 현재 슬롯 연결 일치 여부이며 향후 본인 수정/통계 권한 검사에 사용합니다.

## 받기와 광고

사전 확인 → 광고 처리 → 실제 서버 실행 순서입니다. 한 사용자/라운드의 광고 이력은 하나입니다. 생성자와 기존 참여자는 추가 광고 없이 받습니다. 미참여 플레이어는 최초 수신 전 광고를 처리합니다. 사용자의 다른 활성 라운드 유무는 종료 기록 수신을 막지 않고 새 활성 참여자를 만들지도 않습니다.

앱은 user_id/action_id/delivery_id를 영속 보관한 뒤 요청합니다. 완료/장애 결과도 로컬에 먼저 기록합니다. 광고 도중 앱 종료는 outcome을 만들지 않습니다. 실제 완료 이벤트가 없는 시간을 광고 완료로 추정하지 않습니다.

광고 처리 결과는 round_ad_settlements에 먼저 보관하고 수신을 별도로 실행합니다. 광고 중 전송이 취소되거나 연결이 해제됐더라도 처리한 광고는 유지하고 수신은 거절합니다. 후속 새 전송에서는 추가 광고를 요구하지 않습니다. 운영 환경은 개발 테스트 결과를 ads_not_configured로 거절합니다.

실행 트랜잭션에서 활성 기기, 요청 사용자, 전송 받는 사람, pending, 현재 슬롯 연결, ended, 광고 이력, 같은 사용자의 활성 개인 기록 부재를 다시 검사합니다. RECEIPT 생성, DELIVERY received 전환, action 완료 저장이 함께 성공해야 합니다.

## 삭제와 재시도

개인 삭제는 receipt.status=deleted, deleted_at만 갱신합니다. ROUND/SCORE/다른 사람의 RECEIPT 및 DELIVERY received 이력을 보존합니다. 목록은 pending DELIVERY와 active RECEIPT를 각각 조회합니다. RECEIPT가 없다는 이유로 과거 전송을 받을 기록으로 복구하지 않습니다.

동일 요청 또는 다른 탭이 같은 delivery를 받은 뒤 재시도하면 같은 RECEIPT를 반환합니다. 그 기록이 삭제됐으면 deleted 상태를 반환하고 재생성하지 않습니다. 새 DELIVERY로 받은 기록은 새 receipt_id이며 예전 삭제 요청으로 삭제되지 않습니다.

동일 사용자/라운드의 active RECEIPT는 하나입니다. tombstone은 이력으로 남습니다. 수신 뒤 해당 참여자의 최근 종료 홈 목록에서 제거하며, 개인 기록에서 라운드 원본 전달 관리로 돌아갈 수 있습니다. 삭제한 과거 기록을 홈 종료 항목으로 다시 띄우지 않습니다.

기기 저장 실패는 성공으로 표시하지 않습니다. 서버 성공 뒤 로컬 확인 저장이 실패해도 원래 수신 요청을 남깁니다. 사용자별 저장소와 웹 탭 잠금으로 요청 교체/삭제 경쟁을 막습니다. 손상된 보류 데이터는 원본을 유지합니다.

수신하지 않고 목록으로 돌아갈 때도 기기에 저장된 광고 결과가 있다면 서버의 광고 이력 등록을 먼저 확인합니다. 통신 장애로 확인하지 못하면 그 결과와 원래 요청을 보존합니다. 이 경로는 광고 이력만 정리하며 기록을 자동으로 받지 않습니다.

## 목록과 읽기 권한

받을 기록, 받은 기록, 라운드 전송 이력은 20개씩 커서로 추가 조회합니다. 같은 시각의 항목은 UUID를 두 번째 정렬 기준으로 사용합니다. 남의 수신 목록이나 개인 RECEIPT는 볼 수 없습니다.

받은 기록의 전체 스코어카드는 전용 읽기 API를 사용하며 공동 점수 입력 권한을 추가하지 않습니다. 개인 삭제된 항목은 metadata만 반환하고 sheet는 null입니다. 개인 목록/전체 열람은 온라인 기능이며 수신 기록의 새 오프라인 캐시를 도입하지 않았습니다. 기존 참여자의 점수 캐시와 미전송 초안은 이전 단계 규칙을 유지합니다.

7단계 자체는 실제 광고 SDK/배너, 개인 통계, 종료+24시간 본인 수정, 신페리오, 이메일, 외부 배포를 포함하지 않습니다. 개인 통계와 본인 수정은 후속 8단계(PERSONAL_RECORDS.md)에 연결했습니다.
